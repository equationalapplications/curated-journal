# Tip jar ("Support Curated Journal") — design

**Status:** Implemented in this PR (stacked on #79, ships in 5.0.0).
**Intents:** `INTENT.md` rules 9 (sandbox traffic), 11 (strict privacy),
and the "any off-device communication in strict privacy" out-of-scope
item. Owner ruling (Kurt, 2026-11-02): users can leave an optional tip by
in-app purchase; if they try to tip in a privacy mode that doesn't
support it, the app shows them an alert.

## Charter check

Before this PR the charter said the default mode's traffic is model
downloads and update checks the user starts — nothing else. A tip is new
traffic the app starts, so on intent this spec contradicted rule 9 and
the strict-privacy list in rule 11. Per `AGENTS.md`, `INTENT.md` is
amended in this same PR rather than designed around:

- Rule 9: tip purchases the user starts join the default mode's
  traffic. The OS store (Apple or Google) handles them; no journal data
  is involved.
- Rule 11 and the out-of-scope item: no tips in strict privacy. Tapping
  the tip jar there shows an alert that says why and how to step out of
  strict privacy. The app never makes a silent network call.
- Status lines: privacy modes are still not built. The tip jar asks a
  single check, and today that check always reports the default mode.

## Products

Consumables with the same IDs on both stores. The consoles are set up
separately from this PR.

| ID | Name in app | Store price (US) |
|---|---|---|
| `cj_tip_coffee_299` | Coffee | $2.99 |
| `cj_tip_coffee_499` | Big coffee | $4.99 |
| `cj_tip_coffee_999` | Coffee for the team | $9.99 |

Prices on screen come from the store (`displayPrice`, localized). They
are never hardcoded. The UI says "Support" and "Buy me a coffee", never
"donation" or "tax-deductible". A tip unlocks nothing, so there is no
entitlement and no receipt verification.

## When the app talks to the store

Rule 11 says nothing that can reach outside may act before the mode is
honored. So:

- `expo-iap` is not imported at launch. `src/lib/tipJarStore.ts`
  `require`s it lazily inside `openTipJar`.
- Rendering Settings does nothing. The section shows a "Buy me a
  coffee" row with an **Open** button.
- Tapping **Open** asks `canUseStorePurchases()` first. If it says no,
  the strict-privacy alert shows and nothing is sent. If it says yes, the
  app connects (`initConnection`), fetches the three products
  (`fetchProducts`, `type: 'in-app'`), and finishes any leftover
  completed tips (`getAvailablePurchases`).
- Each tip tap asks the check again, because the mode may have changed
  since the jar opened. Then it calls `requestPurchase`.
- The connection closes (`endConnection`) when the section unmounts.

Why connect on **Open** and not on the purchase tap: localized prices
need the store, and showing a price before the user commits is the
honest UI. **Open** is already an explicit user tap and comes after the
mode check, so this is still "connect on tap". It is not launch-time and
not background. Connecting only on the purchase tap would mean
hardcoded prices, and that is ruled out.

## Purchase outcomes

- Purchased: `finishTransaction({ purchase, isConsumable: true })`, then
  a "Thank you!" sheet. Without the consume step, Google auto-refunds
  after 3 days and the tip can't be bought again.
- Pending (Android pending payments, iOS Ask to Buy / deferred): status
  copy only, no finish. The tip finishes the next time the user opens the
  jar, never in the background.
- Cancelled: silent.
- Store unavailable, network error, or other failure: fixed copy. Raw
  store messages are never shown.
- Already owned (an unconsumed earlier tip): that tip is finished now.
- Finish failed: copy says reopening the jar finishes it, since the store
  replays unfinished transactions.
- Duplicate delivery of one transaction (listener plus
  `getAvailablePurchases`) is finished once per transaction id.

## Privacy-mode helper

`src/lib/privacyMode.ts` exports `getPrivacyMode()` (always `'default'`
today), `canUseStorePurchases()`, and `canOpenSupportLink()`. It is the
one place the mode system (ROADMAP Step 2) has to change. The alert uses
the app's confirm sheet (`useConfirmSheet`), which is the themed
`Alert.alert` equivalent and also renders on web, where RN-web's `Alert`
does nothing.

## Platforms and native guard

- iOS and Android: in-app purchase through `expo-iap` with the config
  plugin, Android store pinned to `play`.
- Web: `tipJarStore.web.ts` keeps `expo-iap` out of the web bundle, and
  the IAP buttons are hidden. A PayPal "Support" link renders only when
  `SUPPORT_PAYPAL_URL` (`src/lib/supportConfig.ts`) is a non-empty
  `https://` URL. It is empty until the owner creates it. Opening it is
  gated by `canOpenSupportLink()` and gets the same alert. The link is
  web-only: store rules forbid steering iOS and Android users to outside
  payment for tips.
- If a binary lacks the ExpoIap native module, the guarded `require`
  fails soft: the jar reports "Tips aren't available right now" and the
  app doesn't crash.

## Versioning

Adding a native module and a config plugin is **MAJOR**
(`docs/VERSIONING.md`). #79 already bumps 4.0.2 → 5.0.0 for the first
store release. This PR is stacked on it and does not bump again, so the
tip jar ships in the same 5.0.0 binary. Prebuild was verified locally:
`openiapStore=play` lands in `gradle.properties`,
`EXPO_UPDATES_CHECK_ON_LAUNCH` stays `NEVER`, and `expo_runtime_version`
stays `5.0.0`.
